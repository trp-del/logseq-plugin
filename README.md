# Logseq Plugin

Six tools for a Logseq DB graph, in one plugin, one look. Each does one job:

- **Look** draws how things look: a link in the text colour that opens its page, in a property's value too, a tag as its name in serif, a page's place in the tree beside its title, an icon of what each property holds.
- **Find** is the search window as the first step of a walk: a name, then the kinds and the time, then the thread from what you found, without leaving.
- **Predictive** fills in properties and predicts pages while you write, and stays out of the way.
- **Ontology** is the map of the graph's tags and properties: one screen to see the whole shape, move things and change many at once, with one Undo.
- **DB Export** takes a page or some blocks out as a PDF, as Markdown or as rich text on the clipboard.
- **Threads** shows, on a page, everything that points at it, named by the property it came through, to follow and dig along.
- **Todo** is Logseq's own tasks as one short list, on a page of its own and in the right sidebar: today, coming up, any time; add one with a day in its words, tick it off.

Built for Logseq 2.0.2 DB graphs. It reads the graph and writes to it only here: Ontology's Apply and its Undo; Predictive's values and tags while you write, on the bullet you leave or on its parent when only the parent's tags give the properties, with a tag on a page you linked and tagged in the words, and a journal page or a next bullet where one is needed; what Look's × takes off; Find's "make a page"; and in Threads a value or a tag changed in a row, a bullet or a page added, the pick bar's Delete, and the Recycle list under troubleshooting, which restores a page or deletes it for good; in Todo a task added to today's journal and a task's status ticked or unticked; and a file handed in from outside (the Alfred workflow), pasted into an empty bullet so it becomes a node of its own. DB Export writes nothing to the graph. One thing is written outside the graph's notes: a key of Logseq's own set on Look's key sheet goes into the graph's config (its `:shortcuts`), by `PluginDoor.setLogseqKey`, which writes the whole list back with the one key changed and writes nothing when the list could not be read. Every one of these writes goes through one place, `PluginDoor.write` in `plugin.js`, which also holds the checks an Undo makes before it takes anything back (a value only while it is as the change left it; a page the plugin made only while nothing is written on it or links to it, and always by its id, never by a name another page could share); `node test/writes.js` fails on a write anywhere else. Each module's own README, in its folder, says what it draws, its keys and exactly what it writes.

## Install

In Logseq, open the command palette and run **Install plugin from GitHub release**. Paste this repository's address, tick the **effect** box, and press Install. Without the tick the plugin runs in a sealed frame and can draw nothing; uninstall and install again with it ticked. **Check update** on the plugin's card brings the next version.

Find, Ontology, Ontology in the sidebar and Todo head Logseq's ··· menu at the top right; Logseq's magnifier at the top left opens Find too. With Look's calm toolbar off, Ontology also has a toolbar icon, pinned from the puzzle icon, listed as `structure-open`.

Or download the zip from the latest release, unzip it, and load the folder with **Load unpacked plugin** (Developer mode, effect ticked).

## Settings

One window for the whole plugin: **Plugin settings**, from **g** then **,** outside a bullet (as Logseq's own g pairs), the gear on the plugin's card (Open settings), the command palette, or Logseq's three dots under Plugins. Down the left, the places where you meet things rather than the six parts that draw them: under *What you see* the window, a page and the right sidebar; under *What you do* writing, finding, following links and taking a page out; under *Everything else* every keyboard shortcut in one list, and the parts (switch one on or off, and find a fault). A place lists its settings in the middle, one line each, with what each is set to at its right end and a dot before it when you changed it. The setting you pick shows on the right, large: its name, one plain line, then every choice as a picture of the thing itself, side by side, each named under it ("Blue", "Underlined"). The choice in force has a firmer edge and a ✓, the one the plugin came with says "as it came", and in each picture only what differs from the other choice keeps its full strength. A press on a picture takes it; Up and Down walk the settings, Left and Right the pictures. A number shows a picture at a few sizes and takes another typed; keys show what pressing them does, and Press new keys records the next keys you press; a list shows its words, each with its ×; your CSS for the PDF changes its picture as you type. A letter typed anywhere finds a setting through every place. A part switched on or off under Parts waits, pencilled, for **Reload to apply**, which brings you back to the window. Changed by you lists what differs from the start. Logseq's plain list is one word away at the foot; it also holds what the export window remembers.

**Update plugins**, from **u** then **p** outside a bullet, or the command palette: every plugin that is switched on comes to its newest; one switched off stays off. One loaded from a folder loads again, so it runs what changed there, and a notice says when it is done. One installed from a GitHub release or the Marketplace is fetched by Logseq's own updater, as Check update on its card does: a newer release is put in and the plugin reloads, and Logseq's notice says it was updated, or that it is up to date. This plugin goes last.

## From outside

The Alfred workflow in the workspace's `alfred/` folder adds things from anywhere on the Mac: words to today's journal, to the open page or to a page by name, and files and pictures into the graph. Words and pages go through Logseq's HTTP API; a file comes to the plugin (`outside.js`, which stands whichever modules run), because the API has no call that makes an asset node: the plugin pastes the file into an empty bullet of the page, as Logseq takes a dropped file, so it becomes a node of its own that Cite finds and Threads lists. The page is shown for a moment while the file goes in and the screen is put back, with the bullet that was being written in; a page named by the caller stays on screen. The call is `logseq.App.invokeExternalPluginCmd` with `["logseq-plugin", "models", "add", [{ files: [paths], where: "today" | "open" | { page: name } }]]`, answered with what was added or an error saying why.

## How it is built

No build step: plain scripts, loaded in the order `files.js` lists. `plugin.js` is the door each module registers at as it loads, and where it describes its rows for the settings window (`settings/`), which belongs to no module, so it works whichever are switched off. The door also holds what every module draws with, each drawn once: the greys and the shared class names, the buttons, the window and the pop-up frames, the tick box, the fold arrow, the bullet, the field, the nothing-here line, the icon of what a property holds, the one Undo (a faded arrow at the end of what changed, or waiting at the bottom right; a new change's arrow takes the last one's place, except that a change of many things, Ontology's Apply or a pick of several nodes in Threads, keeps its own arrow until the next change of many things, so filling in one value never takes it away), the one watcher of Logseq's screen (no module keeps a watcher of its own), and the one motion of what opens: it rolls out from nothing so what is below glides down, rolls back up when it closes, and stands still under reduced motion. Since 10 November 2026 the door also holds the groundwork every module stands on, each kept once: the module's base (`PluginDoor.base`: its stylesheets sent only when changed, its settings read with their defaults, its listeners on Logseq's window, Logseq's hooks and its passes on the screen watcher, all taken off again when the module stops), the one way to work Logseq's own menus and boxes (`PluginDoor.screen`: a press, a key, words typed into a box, whether a pop-up of Logseq's is open), the one date service (`PluginDoor.dates`: a day in words, "Oct 23" and "Oct 23, 2025" for another year, a journal's title in the graph's date format, the journal page of a day) and the small readers of the graph (the id pattern, `bare`, `pick`, `idOf`, `query`, the Apple helper's address). `main.js`, loaded last, gives Logseq every module's settings as one list, sends the shared names, keeps Logseq's frame in place (a focus that pushes it up is put back) and sets up the clean-up and the ways into the settings window before anything else; then it starts the modules one after another. One failing, or not answering, is said in a notice and leaves the rest running; every module that began is stopped; a file that did not load is named in a notice. Each module lives in its own folder (`look/`, `find/`, `predictive/`, `structure/`, `export/`, `threads/`, `todo/`) and keeps its code under a name of its own on the plugin's window, so the modules never touch each other's.

The six were written as six plugins and joined into one on 31 October 2026. This is now the only copy that changes; the six old folders are an archive.

## Checks

Each module keeps its own in its folder: `test/` for what runs without Logseq, `tools/app/` for driving the real app. Run all of them with

```
NODE_PATH=<a folder holding jsdom and Playwright> sh test/all.sh
```

`test/module.js` and `test/start.js` load one module the way `main.js` does, so a module can be checked alone. `test/writes.js` checks that every write goes through the one write path, and `test/risks.js` the seven data-safety fixes of 10 November 2026. Six more hold the groundwork in place, each failing on a copy made anywhere but the door and then trying the door's own piece: `test/base.js` (a stylesheet, a setting's reader, a hook of Logseq's or a listener outside a module's base), `test/watcher.js` (a second watcher of the screen), `test/screen.js` (a made-up press, key or input not sent through the screen door), `test/dates.js` (a date rule of a module's own), `test/keys.js` (a pressed key read, a setting's keys matched or Logseq's own keys reached by a rule of a module's own) and `test/helpers.js` (a copied helper, Apple's helper asked by lines of a file's own); `test/ground.js` is what they share. With Logseq open on the Illness Test Graph, `node tools/write-check.js` makes every kind of write in the real app, reads it back and proves the graph ends as it began. Threads' slow checks: `cd threads && sh tools/check.sh --full`. `node tools/app-check.js` checks the whole plugin in the real Logseq, read-only.

`node tools/motion-check.js` measures what the plugin draws moving in the real Logseq and says what caused each fault. Every stop (a page, `sidebar:<page>`, `find`, a route such as `#/structure`) is recorded with the plugin off and on: every element a module marks and Logseq's own landmarks frame by frame, the browser's layout-shift log and the screencast's pictures (`tools/frame-kit.js`, the kit Threads' pretend-page frames test uses too). A jump, a flash, a piece that comes late, a page that settles later than without the plugin, a long frame with the plugin's code in it, or an element out of place (a tag off the bullets' one right edge, a day off the margin's edge, a chevron off its column, anything past the pane's edge or over Logseq's words) is a fault, run again twice before it counts. Each fault is laid to a module by the mover's marks and to a cause from the ledger (what came or grew above it in that frame); with `--blame` the stop is recorded once more with a log of every change to the page and the script that made it, and the fault is laid to a file and function. It writes nothing to the graph and puts the app back as it found it. Reports and pictures go to `dist/motion-check/`; the findings still open are listed in the workspace’s `history/reviews/open-motion-issues.md`.

`node tools/view-change-check.js` records every view that redraws, frame by frame, in the real Logseq (the Item tab from row to row, the sidebar's tabs, the Ontology tab from tag to tag, Linked folding, the map's views, Find, the settings and export windows) and fails when the changing area stands blank or half drawn in between. It reads only; `test/review.js` holds the fixes of the 12 November 2026 review in place without the app.

## Releasing

By hand, with no GitHub Actions. Raise the version in `package.json`, then:

```
sh tools/release.sh
```

That builds `dist/logseq-plugin-v<version>.zip`. Tag the commit `v<version>`, push, and on GitHub draft a release of that tag with the zip attached. Logseq's installer takes the latest release's zip.
